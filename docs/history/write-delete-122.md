Issues #123–#134 plus #136: the write and delete seams stopped being issue #64's
blanket context-keyed refusal and became translating seams with a policy of their
own (ADRs 0016–0020). Includes the on-disk oracle work and the `feat/delete-write`
review-fix batch.

**Update (issue #133):** `tests/real_core/write_delete_oracle_test.c` (new) is the on-disk oracle #122's write/delete series calls for: the recording-stub suite (`write_delete_conversion_test.c`, issues #64/#128/#130) proves the write and delete *policy*, but a shim round trip cannot verify a sign flip, a stored spelling, a stamp, or a fan-out — ADR 0016's own "Consequences" section says why (a write flips HLI→stored and a read flips stored→HLI, so the caller's own value returns unchanged whichever sign, spelling or fan-out actually reached disk) — so this file reads the *copied* fixture directly with HDF5, never through the shim, after asking the shim to mutate it. Implementing it surfaced a real defect rather than a test-writing question, now tracked as issue #136: on the pinned real IMAS-Core version (5.7.1), `HDF5EventsHandler::beginAction` initializes the *reader's* per-IDS HDF5 group only under a `READ_OP`-opened context; a `WRITE_OP`-opened context (`al_begin_global_action`/`al_begin_slice_action` alike) only initializes the *writer's* group. Stored-DD-version discovery (`version_stamp::discover`) reads the stamp through the same ctx_id a seam has just opened, so through a `WRITE_OP` context that read comes back `size == 0` — not an error, just not-found — and `decide_occurrence_registration` treats that exactly like a genuinely unstamped occurrence (ADR 0007's presumption), registering nothing; every write or delete issued through that context is then a plain, untranslated forward. The obvious workaround does not exist: a write through a `READ_OP`-opened context (which does discover and register correctly) fails with a real Core exception, since the *writer's* group was never initialized for it, and opening the same occurrence twice does not help either, since `StampOutcome::Unstamped`'s `OccurrenceCacheEffect::Forget` erases what the first open's successful discovery cached. So of #133's five planned on-disk claims, only the fifth — "a refused write leaves no trace on disk" — is provable against this real Core version, since a refusal is decided entirely from registry state before Core is ever touched and therefore needs only a context real Core can actually register (`READ_OP`, not the `WRITE_OP` a literal reading of the claim might suggest); `write_delete_oracle_test.c` proves it in both fixture directions by reading the DD-version stamp raw off disk after a refused write, and `scenario_write_op_root_does_not_register_a_mismatch` pins today's gap as a regression marker that will start failing once #136 lands — the signal to replace it with the four deferred claims. Real-core-labelled test count 18 → 21; full real-Core profile 205 → 208; the stub-only profile is unaffected at 183, since `write_delete_oracle_test` is a real-Core-only target, gated the same way `equilibrium_read_test` is.

**Update (issue #136):** stored-DD-version discovery now asks a context of its own whenever the caller did not open theirs `READ_OP` (ADR 0020), which makes the whole write-path policy ADR 0016 specifies reachable from a real write-capable caller for the first time. #133's paragraph above describes the defect exactly and is left standing as the record of it; what it calls a permanent gap is what this issue closes. `interpose::open_occurrence` gained an `rwmode` parameter and, ahead of forwarding the caller's own open, calls the new `probe_stamp_through_a_read_context`: a shim-owned `READ_OP` global action on the same pulse and occurrence, read through the same unconverted `al_read_data` `version_stamp::discover` already used, then closed. Four decisions in it are load-bearing and each is argued in ADR 0020 rather than here — the predicate is `rwmode != READ_OP` rather than `== WRITE_OP` (a list of the ABI's non-read modes is a list this project does not own); the probe runs *before* the caller's open rather than as a fallback after it, because `HDF5Reader::close_file_handler` sets the pulse's shared `opened_IDS_files` entry to `-1` and a probe closed after the caller's write context exists would pull that handle out from under it; the probe opens and closes through the *plugin* call family, since `al_begin_global_action` is `al_plugin_begin_global_action` plus plugin registration and binding and a context no HLI will ever see needs neither; and it is always a *global* action, so the slice and time-range seams trigger a global probe rather than asking a time-shaped context for a non-timed `STR_0D`. `seam_policy` is untouched: `decide_occurrence_registration` still receives one `FnOnce() -> StampOutcome` and still knows nothing about how the stamp was obtained, so ADR 0015 holds. No stub-observable behavior changes, and that is structural rather than lucky — every recording-stub scenario that opens an occurrence with a latched HLI DD version opens it `READ_OP`, so no probe fires anywhere in that suite. `docs/adr/0016-write-path-seam-policy.md` decision 11 gains a correction paragraph: its policy claim was right and the mechanism under it was not.

Implementing #133's four deferred on-disk claims on top of that surfaced three further real-Core facts, one of them a segfault fixed here and two filed. **Fixed here:** `interpose::delete_candidates`' presence probe passed a null `*data` for a `DOUBLE_DATA` `dim == 0` read, and IMAS-Core's scalar ABI requires the *caller* to own that buffer — `Lowlevel::setValue` copies the stored value into `**data` and frees its own allocation, `Lowlevel::setDefaultValue` writes `EMPTY_DOUBLE` into `**data` for an absent field, and both dereference unconditionally — so the probe crashed real Core rather than being told not-found. Reachable before this issue too, through a plain `READ_OP` mismatched context plus an `al_delete_data` on a `merged`/`split` path, so it is a pre-existing defect rather than one this change introduced. The probe now owns a stack `f64` and classifies through a new `read_outcome::classify_scalar_double`, which delegates to the existing pointer-based `classify` and adds the sentinel as a second not-found channel — both channels rather than only the sentinel, because the layer below is free to answer either way and the recording stub answers with the null pointer. `EMPTY_DOUBLE` moved from `seam_policy` to `read_outcome` and is now shared by the two seams that need it for opposite reasons (a scalar read has no other way to report absence; a value transformation must leave the sentinel alone). **Filed, not fixed:** issue #138 — `delete_candidates` probes through the *caller's* context, so the same reader-group gap this issue fixed for discovery makes every candidate report not-found under a write-mode open, no delete is forwarded, and the fan-out returns `code == 0` having done nothing, which is exactly what ADR 0016 decision 1 forbids; issue #139 — `HDF5Writer::deleteData` ignores its `path` argument entirely and deletes the whole IDS pulse file plus its master-file link, so ADR 0017's per-path fan-out has no per-path effect on the only backend that implements delete at all. The two interact: #138's silence is currently what stops #139 from destroying an occurrence, which the pinning scenario asserts explicitly by noting that the same call *does* destroy `equilibrium.h5` when the conversion record is taken away.

`tests/real_core/write_delete_oracle_test.c` replaces its single regression marker with nine scenarios and proves four of #133's five claims: the stored spelling holds the value and the HLI spelling was never created (`rename-beta-normal`, both directions), the sign on disk is the stored version's convention (`global_quantities/ip`, both directions), the DD-version stamp still reads the stored version after every successful `put_slice` (asserted inside each of those rather than once on its own), and the precedence-2 candidate is left exactly as it was by a write (`split-psi-axis`, reverse direction, with the forward direction's counterpart proving ADR 0016 decision 2 refuses a non-primary *source* and leaves the disk untouched). Two further real-Core constraints shape the file and are stated in its header: every successful write is a `put_slice`, because a `WRITE_OP` *global* action takes `HDF5Writer::write_ND_Data`'s non-slice branch whose `create()` is a bare `H5Dcreate2` and so fails on every dataset the fixture already holds, while the `SLICE_OP` branch checks `H5Lexists` and opens; and the appended slice deliberately carries no `time` value, because real IMAS-Core segfaults inside `al_write_data(op_ctx, "time", ...)` through a slice-mode operation context with matching DD versions and the shim doing nothing at all. Every one of the nine scenarios was confirmed to fail with the probe disabled — the fix is load-bearing for all nine, not just the discovery ones — and each of twenty individual assertions was confirmed red under its own mutated expectation. Review of this issue changed the shape of its proof rather than its code, and two of its findings are worth recording. First, ADR 0020's four decisions were provable only against real Core, which left the stub-only CI job — the one thing keeping the CMake path honest — covering none of them; six new `version_discovery_test.c` scenarios now do, observed through the stub's *plugin*-call recorder, since decision 3 has the probe use IMAS-Core's plugin-free `al_plugin_*` primitive and nothing else in that suite calls that family. `WRITE_OP`, `REPLACE_OP` (decision 1's whole justification for the `!= READ_OP` predicate, and otherwise uncovered anywhere in this project) and all three occurrence-opening seams are covered; the two scenarios that pin what the probe *asks for* refuse it with `RECORDING_STUB_PLUGIN_GLOBAL_FAIL`, because `record_plugin_call` resets its integer fields on every call, so the probe's own rwmode is readable only while its open is the last plugin call made. All five write-mode scenarios fail with the probe disabled, and `read-mode-open-does-not-probe` fails when the predicate is made unconditional — the two mutations together pin the predicate from both sides. Second, `forward-write-through-a-non-primary-source-refuses` originally claimed a refused write "left the disk untouched", and measuring it showed that is false: the caller's own `al_begin_arraystruct_action(size=1)` widens `time_slice` before any leaf write is attempted and IMAS-Core commits that shape at end-action time regardless, so a refused write leaves **one empty appended slice** — every leaf dataset unchanged, the container one element longer. That is the on-disk form of a limitation this project had only ever stated in prose (a shim refusal aborts the put where it stands, with no rollback), and it is now asserted rather than glossed. Also from review: the third refusal ADR 0016 names now has a real-Core scenario (`forward-write-with-no-stored-slot-refuses`, on the `right_only` `q_min/psi`) and all three refusals assert the shim's exact message rather than only its code; `fresh-occurrence-write-is-untranslated` covers the one case the probe can never learn anything from, proving a full `put` into a brand-new occurrence still reaches disk spelled the HLI's own way; the delete-gap marker asserts `deletion.code == 0` explicitly instead of through `CHECK_OK`, since that success is the defect #138 tracks and not a contract to endorse; `write_delete_conversion_test.c`'s shim round trip is now labelled a consistency check, which is an issue #133 acceptance criterion its own PR left open; and the discarded status of the probe's own close is now stated in code and in ADR 0020 decision 6 as a deliberate trade — one leaked IMAS-Core context beats denying the caller's open for a reason they can neither see nor act on.

Counts: `cargo test` 182 → 183 unit tests, the real-Core ctest profile 210 → 224 with real-core-labelled 21 → 29, and the stub-only profile 185 → 191.

**Update (issue #134, closing the #122 write/delete series):** across #123–#133 and #136 the write and delete seams stopped being issue #64's blanket context-keyed refusal and became translating seams with a policy of their own. Each behaviour below is traceable to the ADR that decided it, because the ADRs are the specification of record and #122 was only the implementation ask.

- **ADR 0014, widened (#123).** The read-depth guard became a *reentry* guard: every seam IMAS-Core can call back through enters one thread-local counter — the data-path family, ordinary and `al_plugin_*` alike, plus `al_write_plugins_metadata`, `al_bind_readback_plugins` and `al_unbind_readback_plugins`, from underneath which IMAS-Core's plugin manager issues its own reads and writes against `ids_properties/plugins/**`. One counter rather than one per family, because a read arriving from underneath a write would otherwise find a read-only counter at zero and resolve an already-stored path as though it were an HLI one. This is what makes ADR 0016's refusals safe to introduce at all: `AccessLayerPluginManager::write_field` ends in `assert(status.code == 0)`, so for that caller a refusal is `abort()`, not a returned failure. `tests/shim/reentry_guard_test.c` covers it with stub knobs, which is the only way it *can* be covered — macOS's two-level namespace means real IMAS-Core never reproduces write-side reentry there.
- **ADR 0012, extended (#124).** A loss entry now carries which operation earned it, drained through a fourth shim-owned export, `imas_mvdd_context_loss_operation_at`.
- **ADR 0016 (#125, #126, #127, #128).** `al_write_data`/`al_plugin_write_data` resolve `field` and `timebase` independently to one stored spelling, keeping relative/absolute child-context semantics and the caller's own `data`/`size`; an impossible write refuses before IMAS-Core with the same message contract a refused read has, naming reason, DD path and both versions, and records an `UNMAPPABLE` loss. An ambiguous plan writes **only** precedence 1 and records every skipped candidate as `POTENTIALLY_LOSSY` after Core succeeds; a non-primary *source* refuses outright.
- **ADR 0017 (#129, #130, #131).** A write asserts a value, a delete asserts an absence — so where a write over a `merged` rule must not fan out, a delete must, or the read path's own candidate fallback would serve a stale candidate as live data after a successful delete. `al_delete_data` translates identity, `renamed` and `moved` leaf paths, fans a candidate plan out in declared order probing each stored path first, admits a *trivial* structure delete but refuses one with an **escaping rule** nested underneath it (decision 4), treats an empty path as the caller's explicit whole-DATAOBJECT migration route, and never retains a loss entry.
- **ADR 0018 (#127).** A write-side value transformation executes on a shim-owned *copy*: the caller's buffer is the HLI's own live IDS field, so flipping it in place would silently negate their data. The shim inverts rather than assuming an involution, and leaves an unset rank-0 scalar alone — `EMPTY_DOUBLE` is negative, so flipping it would pass IMAS-Core's `data_has_non_zero_shape` gate and store a fabricated measurement with `code == 0`.
- **ADR 0019 (#126).** A refusal is only safe if someone catches it; decision 5 records the residual exposure where nobody does. Its HLI-side half is deliberately *not* a dependency: IMAS-Fortran's generated `put`/`put_slice` routines have no refusal-tolerance branch, so against an unmodified upstream HLI a refused write tears the time slice, which decision 4 makes a documented limitation of this shim rather than a defect in it. Filed as `yohannmarguier/IMAS-Fortran#61` by issue #134, and stated for users in README.md's "Scope and limitations" — where ADR 0019 asked for it and it had never appeared.
- **ADR 0020 (#136).** Stored-version discovery asks a *read-mode context of its own* whenever the caller's `rwmode` is not `READ_OP`, because real IMAS-Core's HDF5 backend initializes a reader only under `READ_OP` and every write through a write-mode open had therefore been forwarding unconverted.
- **The on-disk oracle (#132, #133).** A mutable real-Core fixture harness, and `tests/real_core/write_delete_oracle_test.c` reading the copied fixture with native HDF5 rather than through the shim — the only way to see a stored spelling, a sign, a stamp or a fan-out, since a shim round trip returns the caller's own value unchanged whichever of those actually reached disk.
- **This issue (#134).** `tests/shim/scoped_passthrough_test.c` closes the validation matrix: the three path-bearing seams ADR 0002 leaves untranslated — `al_get_occurrences`, `al_list_filled_paths` and `al_bind_plugin`/`al_unbind_plugin` — now hold their passthrough contract while a *write* converts as well as while a read does, each scenario first proving the write translates so the claim is made under the condition it is about, and `al_list_filled_paths` keeping #69's seeding of the *stored* spelling so an up-conversion would be visible rather than pass against a string no rule could touch.

Two consequences stay **documented rather than coded**, deliberately, because ADR 0011 forbids inventing a rule for a case the shipped artifact cannot reach — an invented rule is uncovered code. First, **`rwmode` is not a policy input** (ADR 0016 decision 11): the stamp decides whether conversion applies, not the access mode, and because this series' scope is append-only a write-mode open never *creates* a mismatch, only inherits one. ADR 0020 does not change that — `rwmode` is now an input to *which context the stamp is read through*, never to whether conversion applies. Second, **`timebase` inherits the read path wholesale** (ADR 0016 decision 10): it resolves independently of `field`, a refusal on either refuses the write, and both feed the fidelity verdict. The named hazard is real but unreachable here — a write whose timebase resolved to a *different* candidate than the neighbours already in the occurrence would attach its value to a different time basis — because in this artifact `time` is identity and no rule touches a timebase path at all. That is the **one open forward exposure** left by #122: the first conversion-map artifact that touches a timebase path must reopen the question rather than assume it settled, and must not read this silence as a decision that it is safe.

Counts: `cargo test` 183 unit tests unchanged, the real-Core ctest profile 224 → 227 with real-core-labelled unchanged at 29 (the three new scenarios are recording-stub tests, which both profiles register), and the stub-only profile 191 → 194. No shim behaviour changed in this issue — every new test asserts what the code already did, and all 34 new assertions were confirmed red under their own mutated expectation, with the test binary deleted before each rebuild so a stale build could not make a red assertion look green. One of those mutations is worth naming: the caller's own `rwmode` reaching IMAS-Core as `31` fails when mutated to `30`, which is what makes it a real assertion rather than a tautology — ADR 0020's probe opens a `READ_OP` global action of its own just before the caller's, so the two could have been crossed.

**Update (write/delete review fixes: P1, P2, P7, S1–S4, S-J1, S-J3/P5, S-J5, S-J6, P8):** the confirmed findings of the `feat/delete-write` two-axis review (`docs/imas-mvdd-write-delete-review-handoff.md`), each re-verified against the code before being touched. Two of the report's own claims did not survive that check and are recorded here so they are not re-raised.

**P1, the only caller-visible defect.** Issue #128 AC2 asks the unwritten candidates of an ambiguous write to reach the loss log *naming the paths*, and user story 22 says why: so a caller can see the risk that another reader of the stored occurrence finds a stale value **under the other spelling**. `ResolvedWriteArgument` kept only a `usize` count of them and `unwritten_candidate_paths` pushed the caller's own `dd_path` that many times, so the one question the entry exists to answer was answered with the one path that is now certainly correct. `WriteCandidate` gains `stored_dd_path` — the complete stored spelling from the IDS root, not the anchor-stripped fragment IMAS-Core receives, since a fragment does not tell a draining caller where to look — and the count becomes the paths themselves. The three affected scenarios in `tests/shim/write_delete_conversion_test.c` now assert `b_field_tor`/`b_tor` beside a written `b_field_phi` (`fold-p2d-bphi`, three-way), `psi_magnetic_axis` beside a written `psi_axis` (`split-psi-axis`), and the same pair under a live arraystruct child, where the entry still carries the complete `time_slice/...` path the caller never typed. All three were confirmed red under the old behaviour with the test binary deleted first. README.md's loss-log section now states the rule the two entry kinds follow, because it is a caller-facing distinction and nothing said it: a read loss and a refused write name *your* path, a successful write's leftovers name the stored ones.

**S-J3 + P5, the guard-order pair.** `resolve_write_path` hoists the shared `Outcome::Refusal` guard above the write-specific precedence guard, on the stated ground that a rule which cannot be served at all must not appear to be merely a collision risk. `resolve_delete_path` did the opposite while carrying a comment describing the write's order as its own, so one rule could earn two different messages at the two seams. The delete now matches, and both comments say what their code does, including that the later `Outcome::Refusal` match arm is exhaustiveness-only. The order was also *unpinned*: #126's fixture gave each of its three paths exactly one guard, so swapping them left it green. A fourth rule — a `merged` rule whose requested path is a precedence-2 `<from>` and whose fidelity in the direction under test is `unmappable`, the only configuration that trips both — now pins it, with a matching delete-side test that also proves the hoist did not swallow the collision guard. Both go red under a swapped order. Like P12 and P14 before them, this is latent for the shipped artifact: no path in `docs/3.39.0--4.1.1.xml` is both a non-primary source and a refusal, since the four `<redefine>` entries name no `merged` rule's target — which is why it is proven by fixture rather than at the C ABI.

**S-J1, the enum with no reader.** ADR 0016 decision 7 decided `ValueTransformation` should carry a `ToStored`/`ToHli` sense so that a write must *request* the inverse rather than assume an involution, but nothing read the field: the write path's correctness came from calling `inverse()`, not from the direction, so a future write path that forgot the call would have stored the caller's own sign with `code == 0`. Deleting the enum would have contradicted the ADR, so `copy_value_transformation` — the write-side executor — now refuses any transformation not directed `ToStored`, making the decision an enforced invariant with one reader. It is unreachable from `run_write`, which inverts first, hence a direct unit test; the transformation is obtained from a loaded fixture artifact rather than hand-built, because `CocosConvention` has no public constructor and a real resolution proves more anyway.

**P2, earned silence on the write path.** ADR 0016 decision 12 claims `Fidelity::Lossy` has no write-side producer, and nothing asserted it. The two write-side fidelity literals are now two named sites — the new `retain_unwritten_candidates` and the existing `finish_write_refusal` — and `a_declared_lossy_candidate_plan_still_retains_a_potential_loss` drives a fixture `merged` rule declared `lossy` in the direction under test, which is the one input that could make the certain bucket reachable, and asserts the seam still records `POTENTIALLY_LOSSY`. That is not a rounding-down: the declared fidelity is a statement about a *read*, where two stored spellings may disagree and the reader cannot tell which they got, while a write puts one value in one slot and risks only that someone later reads the untouched one. The C-side half — a guard buried in one scenario — is promoted to `check_no_write_lossy_verdict` in the shared header and now drains the whole log in all three candidate-plan scenarios.

**S4 and S-J6, test-infrastructure debt.** `loss_count` was defined five times, `check_loss_at` four, and the newest copy of `check_loss_at` had a fifth parameter (#124's loss operation) the other three lacked — the exact divergence `tests/support/shim_test_support.h` exists to prevent, and CLAUDE.md's "a new copy starts that over" names it. Both are promoted to the shared header in the five-parameter form, so the seventeen read-side call sites now assert the operation where they previously asserted nothing; that retires `check_loss_operation_at`, whose three call sites each sat directly beneath a `check_loss_at` on the same context and index. The recording stub's two data-event kinds get names (`IMAS_MVDD_STUB_DATA_EVENT_READ`/`_DELETE`) beside the data-type codes, with a comment in `tests/stub/recording_stub.c` pointing back, since `tests/stub/` ships no header and the values cross a `dlsym` boundary with no compile-time link. Three `52 /* DOUBLE_DATA */` literals in the same suite become `IMAS_DOUBLE_DATA`. Note for whoever picks it up: 38 more such literals remain in older suites while `tests/README.md` already says to use the macros — a half-finished migration, out of this batch's range.

**S2, S3, P7, and the ADR headers — doc comments that outlived their code.** `tests/owned_exports.def` is `tests/abi/owned_exports.def` (four sites in `src/lib.rs`, plus two `.def` paths in `src/core/core_binding.rs` that the same sweep found). `contextual_refusal`'s doc described the delete seam's blanket context-keyed check as current when #129/#131 replaced it with real path resolution and left the helper with two arraystruct call sites; it now says what its callers are and records the retired one as history. The crate-level doc in `src/lib.rs` still described the #125/#126 intermediate state, where candidate plans and value transformations refused — false after #127 and #128 — and pointed at `src/interpose.rs` for the policy that ADR 0015 moved out; both are corrected, delete included, since "structures refuse" predates #131. ADRs 0016, 0018 and 0019 each still opened with "no code implements it yet". The previous review round produced this same batch (its S1/S5), which is the second consecutive round to do so, so the standing lesson is worth more than the sweep: **a doc comment naming a ticket, a file under `tests/`, or another module's responsibilities is a claim that decays, and the cheapest time to check it is the PR that makes it false.**

**Two findings deliberately not acted on, and one investigated instead.** **P6** claimed `is_equilibrium_leaf` would misclassify a future IDS's structures as leaves and skip #131's escaping-rule check; the failure direction is backwards. A foreign path is absent from the equilibrium inventory, so the function returns `false`, and at its one call site `false` *arms* the check rather than bypassing it — fail-closed, worst case a spurious refusal, and unreachable anyway since `known_artifacts::lookup` returns `None` for any other IDS. **S-J4**'s placement objection to the same `include_str!` survives but is already documented at the function with ADR 0013 decision 6 cited, so it stays a preference. **S-J5** is accurate — `run_delete` relabels a finished `DeletePath` and holds no decision, has no unit test because there is nothing to test, and clones two `String`s the type it reads already owns. It stays anyway, and `seam_policy.rs`'s module doc now says so rather than omitting delete entirely: all three data-path seams presenting the adapter one argument-in/verdict-out shape is what the thinness buys, and a reader should not have to discover that delete is reached differently. **P8** is real but latent: the delete presence probe reads every candidate as a rank-0 `DOUBLE_DATA` scalar, and 8 of the ~10 fan-out targets the shipped artifact can reach are FLT_1D or FLT_2D. What real Core answers for a rank-0 read of array data is not recorded in the inventory doc, the probe cannot reach Core meaningfully until #138 lands, the recording stub is shape-blind and so cannot witness it either, and neither the artifact nor ADR 0013's inventories carry a rank to fix it *with*. It is documented where the decision lives — ADR 0017 decision 2 and the probe itself — and left to #138, whose own notes already name it and raise dropping the probe as an option.

**P3 needed no work:** it reports `tests/shim/scoped_passthrough_test.c` as untouched with no write coverage, which was true at the review's fixed point (`6fbe7ea`) and was closed shortly after by PR #141 — issue #134's own passthrough work — whose three `writing-*` scenarios prove each untranslated seam holds while a write converts. **P4 stays blocked on #138** as the handoff states, and its regression marker is left exactly as it is.
