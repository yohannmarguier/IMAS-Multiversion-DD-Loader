Splitting `src/resolve.rs` into the layers ADR 0015 names: parts A (#105),

**Update (issue #105, part A of the #101 series):** `src/resolve.rs`'s first 650 lines — the ADR 0001 runtime binding — moved verbatim to `src/core_binding.rs`, the file ADR 0015 already names for it: the 25 `extern "C"` fn-pointer types, the `core_binding!` manifest macro and the `CoreBinding` it generates, `VersionDrift`/`ResolutionError`, the `CORE` `OnceLock` and `resolve()`, `SymbolResolver`, `library_path`/`bare_soname`, the `check_major_version` gate, the `const2str`/`err2str` fallback tables and their constant IDs, `failure()`, the six plain accessors `lib.rs` calls directly (`get_backend_id`, `build_uri_from_legacy_parameters`, `const2str`, `err2str`, `get_al_version`, `get_dd_version`), and the nine unit tests covering `library_path`, `check_major_version` and `failure`. `resolve.rs` keeps every seam and falls 2790 → 2129 lines. No function body changed: the only edits to moved code are visibility (`CoreBinding` and its generated fields, `core()`, `DOUBLE_DATA_ID` and `CHAR_DATA_ID` become `pub(crate)`) and the `forward_status!` macro, which now expands `$crate::core_binding::core()` — `macro_rules!` is not hygienic for paths, so the expansion must name the function from wherever it lands — and is re-exported by `pub(crate) use forward_status;` so `resolve.rs` can `use crate::core_binding::forward_status`. That macro is the only *control* crossing the two files; what else crosses is data — `CHAR_DATA_ID`/`DOUBLE_DATA_ID`, compared against by `version_stamp.rs` and `resolve.rs`'s sign-flip type check, and the six accessors `lib.rs` mirrors straight out. `SHIM_READ_DEPTH`/`ReadDepthGuard` deliberately stayed behind even though they sit inside the moved line range: they enforce ADR 0014, not 0001, and ADR 0015 puts the depth guard in the interposition layer because it gates whether policy runs at all. The C ABI suite is untouched — no assertion added, removed or edited, 166 tests with 17 real-core labelled, all green — which is the whole regression net for a move; `cargo test`'s 161 unit tests are unchanged in number and split 9 to `core_binding`, 8 left in `resolve`. That gate is why three prose comments under `tests/` still say `src/resolve.rs` hand-transcribes `al_const.h`'s id-to-string tables when those tables now live in `core_binding.rs` — `tests/real_core_abi_core_check.c:20` and `:66`, and `tests/abi_fallback_constants.def:1`. The series gate ("not one assertion added, removed or edited") would have permitted a comment-only correction, but AC4 is the stricter of the two and asks for a byte-identical suite, which is also the property a reviewer can check mechanically on a move; part C's rename of `resolve.rs` forces that sweep anyway. Both review axes flagged these independently, so they are deferred deliberately rather than missed. `CMakeLists.txt`'s bare-soname comment and `README.md`'s layout table, which are not the test suite, are corrected here. Renaming `resolve.rs` itself is part C's work, when there is something to rename it to.

**Update (issue #106, part B of the #101 series):** `Outcome` was interpreted at three independent sites in `src/resolve.rs`, each deriving a different subset of its meaning — `translate_down` derived a `CString` or nothing, the read seam derived a fidelity-and-candidates read plan, and the context-opening seams derived one concrete spelling, no-source, or a refusal. New `src/path_conversion.rs` is now the one place that answers *what stored path does this HLI argument mean, and at what fidelity* — it knows nothing about seams, attempts, loops or IMAS-Core. Moved in: `resolve_read_path`, `resolve_context_path`, `claimed_argument`, `ReadArgument`, `ClaimedArgument`, `ContextPathResolution`, `ReadPath`, `TranslatedReadPath`, `ResolvedReadPath`, `ConcreteStoredPath`, `stored_anchor`, `concrete_stored_path`, `translated_read_component`, `stored_c_path`, `read_fidelity`, `translated_read_fidelity`, `join_hli_path`, `strip_anchor`, `refusal_reason_message`, and a new `datapath_translation` that carries out exactly the narrow `Outcome` match `translate_down` used to inline. `stored_c_path` was not named in the issue's move list but had to travel with `resolve_context_path`/`translated_read_component`, its only two call sites, both moving; keeping it in `resolve.rs` would have meant `path_conversion.rs` calling back into the interposition layer it's supposed to sit beneath. `TranslatedReadPath`/`ResolvedReadPath`'s fields are `pub(crate)` for one reason: `resolve.rs`'s read loop still turns each candidate into a `ReadAttempt` — a raw-pointer, C-touching construct `path_conversion.rs` deliberately does not know about — via an `impl TranslatedReadPath` block that stays in `resolve.rs` (Rust's orphan rule permits an inherent impl on a foreign same-crate type from anywhere in the crate). `resolve_arraystruct_argument`, `read_data_impl`, `ReadAttempt`, `validate_value_transformation`/`apply_value_transformation`, `live_conversion_record`, and the refusal/loss-log plumbing (`read_refusal`, `contextual_refusal`, `retain_read_fidelity(ies)`, `joined_argument_path`) all stay in `resolve.rs`: the read loop, value-transformation execution, and discovery/registration are issues #107–#109's scope, not this one. `concrete_stored_path`'s doc comment now states its two consumer-side narrowing rules explicitly — a structure path may carry neither an ordered candidate plan nor a value transformation — and why `conversion_map.rs` cannot state them itself: both depend on what the *consumer* can do with an `Outcome`, not on what the rule declares, since the same `merged` rule serves a read (which tries candidates) and would refuse a bare structure-path resolution on the identical outcome. `src/resolve.rs` falls 2129 → 1616 lines; `path_conversion.rs` is 582 lines including its own unit tests, which cover `resolve_read_path` (the not-found-for-an-unclaimed-path proof, issue #56's user story 47) and `join_hli_path`/`strip_anchor` — moved verbatim from `resolve.rs`'s test module, since they test only what moved. `resolve.rs` keeps the one remaining registry-related unit test, `a_data_path_seam_answers_before_the_registry_when_conversion_is_disabled`, since it tests `live_conversion_record`, which stays. `cargo test`'s 161 unit tests are unchanged in count. The C ABI suite is untouched — no assertion added, removed or edited, 166 tests with 17 real-core labelled, all green. A grep for `Outcome::` finds arms only in `path_conversion.rs` and `conversion_map.rs` within the shim's seam-policy code; `src/bin/validate_equilibrium_coverage.rs`, a separate coverage-reporting binary predating this issue (from the P2 review-fix batch) and untouched here, also matches on `Outcome` for its own unrelated purpose and is outside this series' scope. **Correction (issue #134).** Two sentences above place the read loop and its attempt type in the interposition layer, which was true when this entry landed and is not true now: the later parts of the #101 series moved the loop out, and `ReadAttempt`, the `impl TranslatedReadPath` block, `validate_value_transformation`/`apply_value_transformation` and `run_read` itself all live in `src/conversion/seam_policy.rs` today. `read_data_impl`, `resolve_arraystruct_argument`, `contextual_refusal`, `joined_argument_path` and `live_conversion_record` did stay in the interposition layer (`src/interpose.rs`), and `read_refusal`/`retain_read_fidelity`/`retain_read_fidelities` no longer exist at all — loss retention is now carried on the verdict `run_read` returns rather than performed by the loop. The "Current path map" at the top of this file is the authority; this note exists so the sentences above are not read as current on their own.

**Update (issue #109, part E of the #101 series):** nine call sites in `src/interpose.rs` used to rebuild a `forward`/`end-on-refusal` closure pair differing only in which of two ABI symbol families they named — the ordinary HLI call or its `al_plugin_*` reentry twin. One `CallFamily` — a two-variant `Copy` enum, `Ordinary`/`Plugin` — now replaces every one of them, together with `ORDINARY`/`PLUGIN` associated constants that name the two values without holding a raw symbol pointer: `CallFamily` never resolves IMAS-Core itself, because several of the nine call sites refuse before ever forwarding at all (`begin_arraystruct_action_impl`'s argument resolution, `write_data_impl`'s mismatch check), and eagerly extracting a resolved fn pointer at construction time would attempt resolution on a path that used to skip it entirely. Six new dispatch functions — `call_begin_global`, `call_begin_slice`, `call_begin_arraystruct`, `call_read`, `call_write`, `call_end` — are the only six places a `CallFamily` value is ever matched against a real symbol name, each forwarding through the existing `forward_status!` macro exactly where the closure it replaces used to fire, so IMAS-Core resolution stays exactly as lazy as before. `begin_timerange_action` and `delete_data` take no `CallFamily` parameter at all: neither has a plugin twin (`al_plugin_begin_timerange_action` is unlinkable upstream; `al_plugin_delete_data` was never resolved), so there is no second symbol to choose between and no `Option<fn>` member is needed to paper over that gap. The six previously-duplicated seam-wrapper pairs collapse into a shared `*_seam`/`*_impl` function plus two one-line public wrappers each (`begin_global_action`/`plugin_begin_global_action` → `begin_global_action_seam`; likewise for slice, arraystruct, read, write and end), so `begin_arraystruct_action_impl` and `read_data_impl` — already shared since issues #67/#68 — change only how they forward, not their shape. `CallFamily`'s doc comment states the property the issue asks for and no more: a family mismatch requires bypassing the `family` parameter threaded through this module's policy functions, and a reviewer sees that bypass, because the six dispatch functions are the only place the symbol choice is made — not that a mismatch is unrepresentable, which it deliberately is not (the calling binary picks the family, not this type). `src/interpose.rs` grows 1453 → 1735 lines, the doc comments accounting for most of it. `cargo test`'s 165 unit tests, the 167-test real-Core ctest profile (17 real-core labelled) and the 146-test stub-only profile are all unchanged in count and green — no assertion added, removed or edited, since every call site's behavior and every refusal message is byte-for-byte what it was before.
