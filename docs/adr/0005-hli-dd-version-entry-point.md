# The HLI DD version arrives through a shim-owned setter that latches on first use

The shim cannot discover the DD version an HLI was built against. IMAS-Core's `getDDVersion()` is deliberately dead upstream — it returns the sentinel `"!!DEPRECATED!!"` and an upstream test pins it that way — so the caller has to say. We decided the HLI DD version arrives through `imas_mvdd_set_hli_dd_version(const char *version)`, the first symbol this project owns rather than mirrors, with `IMAS_MVDD_HLI_DD_VERSION` as an environment-variable default. The value **latches on first use**: the first version to arrive is the version for the life of the process, an identical later report is accepted, and a *conflicting* later report is refused with both versions named in the `al_status_t` message.

The HLI DD version is a property of the **calling binary**, not of the user or the process. IMAS-Fortran and IMAS-CPP generate their data structures from one DD version, so that version is a compile-time constant in the compiled HLI. The setter does not ask the caller a question; it reports a constant the caller already holds. This is why nothing needs to change it later, and why latching costs nothing.

Being compiled is how those two HLIs satisfy the premise, but it is not the premise. What this design requires of a client is **one DD version for the life of the process** — and, separately, that the client does not already convert DD versions itself. Nothing here is about the source language: the seam is the C ABI, and any caller that reaches it is a client whatever it is written in.

The latch exists because a shared library's writable data is private per *process*, not per caller. Two programs built against different DD versions run as two processes and each gets its own copy of the shim's state — that case needs no support and works by construction. But one executable that links two HLIs built against different DD versions gets **one** mapping of the shim, keyed on soname, and therefore one version slot with two callers disagreeing about it. Without the latch the shim would silently take one of them and translate the other caller's DD paths as if it were the version it is not, returning wrong physics with `code == 0`. The shim cannot split its own writable data — the OS loader fixes the number of copies before any shim code runs — so detecting the conflict is the only defence available, and the error message must name both versions and state that one process holds two HLIs. A message saying only "version conflict" leaves the user as blind as they were, since nothing at the call site reveals that the library is shared.

## Considered Options

- **Per-data-entry scope, keyed on `dectxID`** — rejected on ordering. `al_begin_dataentry_action(uri, mode, dectxID)` hands the context id *back* to the caller, so a per-entry setter can only be called after the entry is open — which is exactly when version discovery has already had to run. It forces the shim to reinterpret contexts that already carry a resolved conversion map.
- **Freely mutable process-global** — rejected. It permits set → open → set → open, producing two entries at two versions through the back door and restoring every question the latch answers, with a disagreement becoming an ordering accident rather than an error.
- **Latch, but ignore later reports in silence** — rejected. Cheaper to implement, but it accepts the silent-wrong-data case for the second HLI, which is the worst failure this design can produce.
- **Latch on first *open* rather than first *use*** — rejected. It permits several conflicting sets before any open and quietly keeps the last, which is the same silent mistranslation moved earlier in the program.
- **Latch on first use; identical repeat accepted; conflict refused** — chosen. An identical repeat has to be accepted because the call is expected to come from an HLI's static initialiser, where the same constant can legitimately arrive twice (several translation units, a library initialised twice, a `dlopen`/`dlclose` cycle). Only a disagreement is dangerous, so only a disagreement is an error.
- **`dlmopen(LM_ID_NEWLM, ...)`, distinct sonames per DD version, or static linking with hidden symbols** — all three genuinely give independent writable data, and all three were rejected as answers to the conflict: each requires the HLI or the deployment to be built differently, none is transparent to the end user, and `dlmopen` is glibc-only, capped at 16 namespaces, and interacts badly with the C++ exceptions and static initialisers that IMAS-CPP depends on.

## Consequences

- **The shim's export list is no longer equal to IMAS-Core's; it is a strict superset.** `tests/check_exports.cmake` currently collects a symbol as public ABI by the `al_` prefix plus four named exceptions, then asserts set equality with IMAS-Core. The `imas_mvdd_` prefix means the filter ignores the new symbol and the check keeps passing — an exported symbol no test verifies, with nothing to reveal it. The check therefore splits into two assertions: every IMAS-Core symbol is present in the shim, and every shim symbol outside that set appears on an explicit list of shim-owned exports. The owned surface becomes something declared rather than something that leaks.
- **The `imas_mvdd_` prefix is the convention for every future symbol this project owns.** The `al_` namespace belongs to IMAS-Core; squatting in it would break the drift check loudly on day one but invites a collision the next time upstream adds a symbol.
- **Unset latches too, and unset means the shim skips version discovery entirely.** No read of `ids_properties/version_put/data_dictionary`, pure forwarding, so the drop-in property stays genuinely free. A setter call arriving after a passthrough open is a conflict and is refused, not applied to later opens. The alternative — discover the stored version anyway and merely decline to convert — costs a read per open and buys nothing until something wants to report the stored version.
- **The environment variable is a default, not a second reporter**, which keeps it out of the conflict rule. The version resolves at first use: a latched setter value wins and the environment is never read; otherwise the environment value is read and latched. The setter therefore always takes precedence and the environment variable can never cause a conflict.
- **A malformed version is a hard failure, never a silent fall back to passthrough.** A bad setter argument returns non-zero immediately. A bad environment value has no call to return from, so it fails the first open. A typo'd version degrading quietly to passthrough is the failure mode this rules out.
- **What counts as malformed is *not* settled here.** The 35 versions in the chain (`3.22.0` … `4.1.1`) are plain `major.minor.patch` triples, but that is a fact about the chain, not about what a caller can legitimately pass. A development build stamps versions like `4.1.1-47-g8eaa5f1`, which is a real HLI DD version and is *newer* than `4.1.1` rather than a pre-release of it. A parser accepting only triples would reject a legitimate dev-DD HLI. The accepted grammar and the comparison function are decided in the version-string policy ticket, which explicitly asks whether the setter's route should be validated more strictly than a recovered stored version; this ADR fixes only that the failure is loud and immediate, not what triggers it.
- **The signature is `al_status_t imas_mvdd_set_hli_dd_version(const char *version)`.** It returns `al_status_t` rather than a plain `int` because the conflict refusal has to name both versions and only `al_status_t` carries a message. It takes a string rather than a parsed triple because the environment fallback is necessarily a string, so a string argument means one parser rather than two.
- **The latch is backed by a `OnceLock`, so first-writer-wins is decided atomically** and the conflict check can never observe a torn value. The setter is safe from any thread. The shim cannot detect a caller that sets on one thread while opening on another — either outcome is legitimate there — so the documented contract is *call the setter before any open*, which an HLI's static initialiser satisfies naturally.
- **imas-python is not a client of the shim, and Python is not the reason.** imas-python does not link `libal` at all — IMAS-Core's own `imas_core._al_lowlevel` extension does, and imas-python imports it (`imas/backends/imas_core/imas_interface.py:17`). More decisively, imas-python **already converts DD versions itself**: it reads `ids_properties/version_put/data_dictionary` (`imas/backends/imas_core/db_entry_al.py:238` — the same field, `CHAR_DATA` at `dim=1`, immediately after a `global_action(READ_OP)`) and feeds `ids_convert`, raising `UnknownDDVersion` on a stamp it does not recognise. Putting the shim underneath it stacks two converters: the shim rewrites the stamp read, imas-python sees its own DD version, and converts a second time from a version the data is not in. It also holds no single process-wide DD version — `DBEntry(dd_version=…)` builds a per-entry `IDSFactory`, so one interpreter legitimately runs several DD versions at once, which is the case the latch refuses by construction. Any of the three is sufficient on its own.
- **The rule is therefore about the client's shape, not its language.** An HLI that performs its own DD conversion is not a client; a caller with no single process-wide DD version is unsupported. A Python program that calls the C ABI directly under one fixed DD version remains a supported client and needs nothing new — with no static initialiser to call the setter from, `IMAS_MVDD_HLI_DD_VERSION` is its route, which is the same route the compiled HLIs mostly take anyway.
- **The shim does not police stacking, because the opt-in default already does.** Unset means pure passthrough, so an HLI with its own converter is served by simply never turning the shim on. Nothing detects or refuses a self-converting caller, and nothing should: which converter an HLI uses is the HLI's decision.
- **Known limitation: the environment variable is process-wide, and the opt-in is not per-caller.** A process that both loads a compiled HLI wanting the shim and runs an HLI with its own conversion applies `IMAS_MVDD_HLI_DD_VERSION` to both. The self-converting HLI never calls the setter, so the latch sees no disagreement and reports nothing, and its reads are silently converted underneath it. This is the one-process-two-HLIs case the latch exists for, with the second HLI's participation invisible. The shim **cannot distinguish callers** — one mapping, one version slot, the same constraint the latch was built under — so detection is not available and documentation is the whole remedy: *do not set `IMAS_MVDD_HLI_DD_VERSION` in a process that also runs an HLI performing its own DD conversion.* Prefer the setter over the environment variable wherever a binary can call it, since a setter conflict is caught and an inherited environment variable cannot disagree with itself.
- **imas-Matlab and imas-Java are not judged here.** Neither `al-matlab` nor `al-java` was available to read, so this ADR records the test rather than a verdict: an HLI is a client if it holds one DD version for the life of the process and does not convert DD versions itself. Whether those two qualify is settled when they are examined. One case is worth flagging in advance — a JVM loading two jars built against different DD versions is exactly the one-process-two-HLIs case, and the latch catches it only if each jar calls the setter.
- **One question this decision leaves open**, tracked on the map: whether IMAS-Fortran and IMAS-CPP have an initialisation hook where the setter can be called. Investigated and answered no — both bake the DD version into the binary as `al_dd_version` and both can reach it before the first open, but neither has a hook that runs by itself, and placing the call means patching two upstream repositories. The environment variable is consequently the main road, not a fallback.
