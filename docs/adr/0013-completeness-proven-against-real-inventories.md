# Artifact completeness is proven against real DD inventories, not a generated coverage summary

Issue #50 (and #43's story 40) asks for "every path is claimed" to be *mechanically provable*, not read off a hand-authored artifact's own `<coverage>` summary — the prototype's equivalent, `validate.py`, could drift from what the rules actually do (`docs/PROTOTYPE_CRITIC.md` §1.5, §1.7). This ADR settles what the proof checks, what it deliberately tolerates, and why.

## Decisions

1. **`ConversionMap::check_completeness` takes two real, checked-in DD leaf-path inventories** (`docs/inventory/equilibrium-3.39.0.txt`, `equilibrium-4.1.1.txt`) rather than trusting the artifact's own `<coverage>` element. The inventories were built from the `imas-dd` MCP server's real path data for the pinned pair, reconciled against version-history `path_added`/`path_removed` events (the server exposes only "latest per major version" snapshots, not each of the 35 individual minor-version listings, so the 3.39.0 inventory is the latest-3.x listing with everything added after 3.39.0 subtracted out).

2. **Two independent checks, both read-only, neither ever called by `resolve`:**
   - *Inventory coverage*: every path in either inventory must resolve (via the existing `resolve`) to an `Explicit` rule match, or to the document-level `Default` match **and** the identical spelling is confirmed present in the other side's inventory too — a `Default` match whose counterpart is missing is a silent, wrong identity assumption, not completeness.
   - *Rule-side backing*: every rule's own primary selector (`left`/`right` — never a `merged`/`split` rule's plural `<from>` candidates, see decision 3) must correspond to something real on its own side: literal membership for `Exact`, itself-or-a-descendant for `Subtree`, at least one match for `Glob`. This catches a rule that names a path with no basis in the real DD at all (a typo, a hallucination) — something the inventory-coverage check alone would never visit, since it only walks paths that are *already* in the inventory.

3. **A `merged`/`split` rule's `<from>` candidates are exempt from the backing check.** They are a precedence-ordered read plan (ADR 0006) that may legitimately name an alias not yet present in an older inventory snapshot. The real artifact's `fold-constraints-j` is the concrete case: its precedence-1 alias, `time_slice/constraints/j_phi`, was only added to the DD in 3.42.0 — it does not exist at all in the true 3.39.0 snapshot — yet the rule is correctly written to serve the whole 3.x lineage feeding into 4.1.1, not only the one pinned snapshot this repository validates against. Six of the artifact's merged rules have this shape; requiring `<from>`-backing would make all six false positives.

4. **The `Subtree` backing tolerance is what proves story 40's named case** — "paths a `retyped`-style rule invents on the right that appear in no path inventory" — without needing any `retyped`-specific carve-out. `retype-coordinates-type`'s anchor, `grids_ggd/grid/space/coordinates_type`, changes DD-side data type from `INT_1D` to `STRUCT_ARRAY` at the 4.0.0 boundary (confirmed via `imas-dd`'s version history); a stricter leaf-only inventory could plausibly list only the new `.../coordinates_type/index` child and not the container itself. The backing check already tolerates an absent anchor as long as a descendant exists (`docs/conversion_map.rs`'s `selector_backed_by_inventory`), so this case is provably covered by the same mechanism `left_only`/`right_only`/`moved` subtree rules already rely on — not a special exception written only for `retyped`.

5. **Running the check against the real approved artifact surfaced four genuine gaps**, not synthetic ones: `bpol_probe` → `b_field_pol_probe`, `mse_polarisation_angle` → `mse_polarization_angle`, and `iron_core_segment/magnetisation_r`/`magnetisation_z` → `magnetization_r`/`magnetization_z`. Each is a simple spelling rename at the 4.0.0 boundary, confirmed via `imas-dd`'s version history (old spelling `path_removed`, new spelling `path_added`, same version) rather than assumed from name similarity. The artifact had no rule for any of them, so each side's paths silently fell through to the document-level identity default — which is exactly the failure mode decision 2 exists to catch. Corresponding `renamed` rules were added.

6. **The embedded equilibrium inventories additionally classify delete arguments as leaves or structures.** `al_delete_data` supplies only a path, so issue #129 cannot safely distinguish a leaf deletion from a container deletion without DD-shape information. Its conversion path therefore consults the HLI-side checked-in leaf inventory solely as a safety guard: membership permits a single-path delete; absence refuses as a structure. It does not select a conversion rule, validate artifact completeness, or alter any read/write semantics. This narrow runtime use is limited to the one embedded equilibrium artifact; a generated artifact must carry equivalent leaf metadata before it can enable converted deletes.

## Considered Options

- **Validate the hand-authored `<coverage>` summary instead of building an independent proof.** Rejected — this is exactly the thing issue #50 asks to stop trusting. A generated summary can silently agree with a rule set that has since drifted from it (`docs/PROTOTYPE_CRITIC.md` §1.5).
- **Require every rule's `<from>` candidate to be inventory-backed too**, for a uniform rule. Rejected — produces false positives against the real artifact today (six merged rules), because a precedence-ordered alias is deliberately allowed to be forward-looking within the version chain.
- **Treat any inventory-absent literal path as invented and reject it, with no `Subtree` tolerance.** Rejected — this is exactly how a legitimate container/shape change (`retyped`) is expressed; removing the tolerance would make every subtree-style structural rule fail, not just invented ones.

## Consequences

- `InventorySide` and `CompletenessViolation` are new public vocabulary carrying real design weight (which failure mode fired, and why two of them exist); this ADR keeps that rationale discoverable rather than living only in `ConversionMap::check_completeness`'s doc comment.
- The checked-in inventories are themselves a small generated artifact (from the `imas-dd` MCP server), not hand-typed prose — a future conversion-map artifact for another IDS or version pair needs its own generated inventory pair before this same proof can run against it.
- For the current embedded equilibrium artifact, the inventories also provide the delete seam's leaf/container safety classification. That second role must move into generated artifact metadata when conversion artifacts become generated; it must not turn the completeness proof into runtime rule selection.
- The proof's own completeness is bounded by the inventory's: if the `imas-dd` data source is itself missing a path (as `docs/PROTOTYPE_CRITIC.md` §1.7 warns can happen), the proof will not catch a gap in that path — it proves the artifact against what the inventory says the DD contains, not against the DD directly.
